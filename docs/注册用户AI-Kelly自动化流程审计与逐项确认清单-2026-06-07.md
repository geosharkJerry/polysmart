## 一、系统目标闭环

本系统的目标运行原理应是：

1. 注册用户完成会员注册、隐私声明同意、邮箱验证与登录。
2. 用户选择服务类型：自助订阅套餐或托管分佣服务。
3. 自助订阅用户通过 Stripe 购买固定点数积分；托管用户走 USDT 佣金结算。
4. 用户在会员面板绑定 Polymarket、Kalshi、PredictIt 等执行账号。
5. 用户完成对应账号钱包充值，本系统同步链上余额和交易权限。
6. 系统抓取 T+0 标的并筛选出当日结算候选事件。
7. AI Agent 对事件进行研判，输出胜率、置信度、摘要与模型来源。
8. Kelly 公式根据 AI 胜率、盘口价格、用户资金、账号可用额度、风险上限生成推荐仓位。
9. 执行服务按账号矩阵拆单，使用库存锁和原子事务提交执行意图。
10. 成交后自助用户按成交额扣点数，托管用户按后台配置佣金比例生成 USDT 结算账本。

## 三、核心缺口总览

当前最大问题不是“模块完全不存在”，而是多个关键模块仍停留在独立能力层，没有形成强制自动化闭环。

| 优先级 | 缺口 | 影响 |
|---|---|---|
| P0 | Kelly 公式没有强制接入注册用户执行路径 | 仓位仍可由外部传入，无法证明每笔执行都由 Kelly 风控生成 |
| P0 | AI 胜率没有写回 T+0 事件池 | 事件池默认概率可能是静态值，后续 Kelly 无真实概率输入 |
| P0 | 执行意图 API 可直接提交任意 legs/notional | 可能绕过 Kelly、订阅、账号权限和风险闸门 |
| P0 | 成交后扣点数/佣金没有自动挂到执行成功路径 | 执行和商业结算没有完全闭环 |
| P0 | 执行相关 API 缺少会员/管理员门禁 | 注册用户自动化流程存在越权风险 |
| P1 | 账号凭据加密仍使用固定开发 key | 生产密钥管理不足 |
| P1 | Live connector 行情可用但真实下单未配置 | 生产态应明确“行情 live / 交易未开通”或接真实适配器 |
| P1 | Stripe 支付成功确认仍缺少 webhook 级最终性 | 后台/接口状态变更可能提前加点 |
| P1 | 自动编排器未形成 `AI -> Kelly -> intent -> execution` | 自动化流程仍需要外部手动串接口 |

## 四、P0 修复项与验收标准

### P0-1：将 Kelly 公式强制接入注册用户交易上下文与执行意图生成

技术实施确认单：`docs/P0-1-Kelly执行计划技术实施确认单-2026-06-07.md`

当前证据：

- `lib/engine/kelly-sizing.ts` 已有 `calculateConstrainedKellySizing`。
- `lib/services/trading-context.ts` 当前使用 `input.targetNotionalUsd` 调用 `sliceOrderAcrossAccounts`。
- `app/api/execution/context/route.ts` 仍要求外部传入 `targetNotionalUsd`。
- `app/api/execution/intents/route.ts` 允许外部直接传入 `legs[].notionalUsd`。

需要修改：

- 新增或扩展 Kelly 执行计划服务，例如 `buildKellyExecutionPlan`。
- 输入应来自：事件 AI 胜率、盘口价格、用户 bankroll、账号钱包余额、可交易账号、现有库存、用户/事件风险上限。
- 输出应包括：Kelly 原始比例、折扣后比例、推荐名义本金、拒绝原因、账号拆单计划。
- `/api/execution/context` 不再接受任意 `targetNotionalUsd` 作为最终执行依据。
- `/api/execution/intents` 必须引用已经生成并通过风控的 Kelly plan，不能直接绕过仓位计算。

验收标准：

- 任意执行意图都能追溯到 Kelly plan id。
- Kelly 输出为 `haltReasons` 非空时禁止生成执行意图。
- 单元测试覆盖：正收益边际、无边际、余额不足、风险 cap 已满、最小下单额不足。
- API 测试覆盖：直接提交任意 notional 被拒绝；引用有效 Kelly plan 成功生成 intent。

确认状态：待用户确认后开发。

### P0-2：将 AI Agent 胜率写回 T+0 事件池

当前证据：

- `lib/engine/ai-router.ts` 可调用第三方 AI 中转站。
- `lib/services/events.ts` 中 `refreshT0PoolFromConnectors` 目前将 `edgeSpreadPct` 和 `aiWinProbability` 写为默认值 `0.5`。

需要修改：

- 事件池刷新后调用 AI Agent 分析。
- 将 `aiWinProbability`、`aiConfidence`、`aiSummary`、`aiProvider`、`aiModel`、`analyzedAt` 写入事件。
- AI 调用失败时必须显式标记为 `AI_UNAVAILABLE`，不能静默冒充真实概率。
- Kelly 计划只能使用已分析或明确降级标记的概率。

验收标准：

- T+0 事件池中每个候选事件都有概率来源。
- 默认 `0.5` 只能作为“未分析/中性占位”，不能进入真实执行。
- 测试覆盖 AI 成功、AI 失败、占位配置、事件跳过。

确认状态：待用户确认后开发。

### P0-3：执行前强制校验会员、订阅、账号、资金与风控状态

当前证据：

- 会员控制台、账号绑定、充值接口已有会员门禁。
- `app/api/execution/context/route.ts`、`app/api/execution/intents/route.ts`、`app/api/execution/submit/route.ts` 未看到会员或管理员门禁。
- `lib/services/trading-context.ts` 会返回 compliance review，但没有强制阻断执行。

需要修改：

- 执行相关 API 接入 `requireMemberSession` / `requireMemberOrAdmin`。
- 会员只能操作自己的 `userId`。
- 执行前必须检查：
  - 用户状态为 active。
  - 邮箱已验证。
  - 订阅状态有效。
  - 自助用户点数余额足够。
  - 托管用户资产池/佣金配置有效。
  - 账号 `canTrade = true`。
  - 账号 `kycStatus = verified`。
  - 系统风险状态允许执行。

验收标准：

- 未登录、未验证、越权 userId、账号未 KYC、资金不足、风险异常均返回明确错误码。
- 测试覆盖会员身份、管理员身份、越权、未充值、未 KYC。

确认状态：待用户确认后开发。

### P0-4：成交后自动触发点数扣费或托管佣金结算

当前证据：

- `lib/services/billing.ts` 已有 `processTradeVolumeCharge`。
- `lib/services/execution.ts` 中 `submitIntent` 成交后只写入 fills/inventory，没有自动调用扣费或佣金结算。

需要修改：

- 自助订阅模式：按实际 `filledUsd` 自动调用点数扣费。
- 托管分佣模式：事件完结或策略结算时自动生成 USDT 佣金账本。
- 扣费失败时应软暂停该用户后续自动执行。
- 扣费/佣金记录需要能在会员面板和后台面板查询。

验收标准：

- `submitIntent` 成功成交后生成 settlement ledger。
- 点数不足时 intent 不应继续进入下一轮自动执行。
- 托管用户不会误扣订阅点数，自助用户不会误进 USDT 分佣账本。

确认状态：待用户确认后开发。

### P0-5：建立自动编排器 `事件 -> AI -> Kelly -> 执行`

当前证据：

- 事件总线 `lib/services/priority-bus.ts` 可以排队和评分。
- 当前未发现一个服务能自动把事件处理结果串到 Kelly plan 和 execution intent。

需要修改：

- 新增自动化编排服务，例如 `lib/services/auto-arbitrage-orchestrator.ts`。
- 输入：T+0 事件、账号矩阵、盘口快照、AI 分析结果。
- 输出：Kelly plan、执行 intent、跳过原因、审计日志。
- 支持 dry-run 和 live 两种模式。

验收标准：

- 单次运行能处理候选事件并输出“执行 / 跳过”的明确结果。
- 所有跳过原因可在后台审计。
- dry-run 不生成真实订单，live 需要生产开关。

确认状态：待用户确认后开发。

## 五、P1 修复项与验收标准

当前证据：

- `lib/services/accounts.ts` 使用固定字符串 `polysmart-dev-key` 派生加密 key。

需要修改：

验收标准：

- 测试覆盖加密、解密、key version。

### P1-2：Live connector 交易能力状态明确化

当前证据：

- `lib/connectors/live-connectors.ts` 中 `placeOrder` 返回 `accepted: false`，原因是 live order routing 未配置。

需要修改：

- 后台系统设置清楚展示：行情 live、交易 mock / disabled / live。
- 未配置真实交易适配器时，执行服务必须 fail closed。

验收标准：

- live 行情可用但 live 交易未开通时，不会误显示“生产可交易”。
- 测试覆盖 connector mode 与 order mode 分离。

### P1-3：Stripe 支付以 webhook 为最终确认

当前证据：

- 当前 `confirmPointsCheckoutSessionAsync` 可由接口确认支付会话并加点。

需要修改：

- 新增 Stripe webhook route。
- 只有 Stripe 签名校验通过且 payment succeeded 后加点。
- 前端手动确认只查询状态，不直接加点。

验收标准：

- 无 webhook 签名不能加点。
- 重复 webhook 幂等。

### P1-4：D1 与 runtimeState 状态一致性

当前证据：

- 多个服务支持 D1 fallback，但部分执行态仍主要在 `runtimeState`。

需要修改：

- 明确哪些运行态必须持久化到 D1：Kelly plan、intent、orders、fills、settlements、audit logs。
- 避免重启后丢失执行证据。

验收标准：

- 重启后仍可查询历史 Kelly plan、订单、扣费和佣金记录。
