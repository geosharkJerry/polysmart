# P0-1 Kelly 执行计划技术实施确认单

生成日期：2026-06-07  
对应审计项：`P0-1：将 Kelly 公式强制接入注册用户交易上下文与执行意图生成`  
当前状态：等待用户确认后开发。本文仅作为技术实施确认单，不代表已经修改业务逻辑。

## 一、修复目标

将当前“外部传入交易金额”的执行模式，升级为“系统根据 AI 概率、盘口价格、用户资金、账号矩阵和风险上限自动生成 Kelly 执行计划”的模式。

修复后，每一笔执行意图必须能追溯到一个 Kelly plan；没有 Kelly plan 或 Kelly plan 不通过风控时，系统不得创建执行 intent。

## 二、当前问题证据

### 1. `TradingContextInput` 仍要求外部传入交易金额

文件：`lib/types.ts`

当前结构：

```ts
export interface TradingContextInput {
  eventId: string;
  userId: string;
  targetNotionalUsd: number;
}
```

问题：

- `targetNotionalUsd` 来自请求参数，而不是 Kelly 公式。
- 这会允许外部调用方绕过仓位控制。

### 2. `buildTradingContext` 直接用外部金额切单

文件：`lib/services/trading-context.ts`

当前行为：

```ts
const executionPlan = sliceOrderAcrossAccounts(input.targetNotionalUsd, accounts);
```

问题：

- 没有调用 `calculateConstrainedKellySizing`。
- 没有把 AI 胜率、价格、钱包余额、风险 cap 作为仓位输入。

### 3. `/api/execution/context` 接受任意 `targetNotionalUsd`

文件：`app/api/execution/context/route.ts`

当前行为：

```ts
const targetNotionalUsd = Number(payload.targetNotionalUsd || 0);
```

问题：

- API 行为仍是“前端/外部指定金额”。
- 不符合“Kelly 公式生成仓位”的核心原则。

### 4. `/api/execution/intents` 接受任意 legs/notional

文件：`app/api/execution/intents/route.ts`

当前行为：

```ts
const legs = Array.isArray(payload.legs) ? payload.legs : [];
```

问题：

- 调用方可以直接提交 `legs[].notionalUsd`。
- intent 没有 `kellyPlanId`。
- 无法证明订单金额来自 Kelly plan。

## 三、建议新增数据结构

建议在 `lib/types.ts` 中新增：

```ts
export type KellyPlanStatus = "APPROVED" | "HALTED" | "EXPIRED";

export interface KellyExecutionPlan {
  planId: string;
  userId: string;
  eventId: string;
  status: KellyPlanStatus;
  side: MarketSide;
  entryPrice: number;
  winProbability: number;
  bankrollUsd: number;
  availableLiquidityUsd: number;
  existingExposureUsd: number;
  maxUserExposureUsd: number;
  maxEventExposureUsd: number;
  rawKellyFraction: number;
  adjustedKellyFraction: number;
  constrainedFraction: number;
  recommendedNotionalUsd: number;
  expectedValuePerDollar: number;
  impliedOdds: number;
  capUsd: number;
  haltReasons: KellyHaltReason[];
  executionPlan: AllocationOutput[];
  aiEvidence: {
    provider: string | null;
    model: string | null;
    confidence: number | null;
    summary: string | null;
  };
  createdAt: string;
  expiresAt: string;
}
```

建议扩展：

```ts
export interface ExecutionIntent {
  intentId: string;
  userId: string;
  eventId: string;
  kellyPlanId: string | null;
  status: "CREATED" | "LOCKED" | "EXECUTING" | "HEDGED" | "FAILED";
  createdAt: string;
  updatedAt: string;
  legs: OrderIntentLeg[];
}
```

建议在 `RuntimeState` 中新增：

```ts
kellyPlans: Record<string, KellyExecutionPlan>;
```

## 四、建议新增服务

新增文件：

`lib/services/kelly-execution-plans.ts`

建议方法：

```ts
export function buildKellyExecutionPlan(input: {
  userId: string;
  eventId: string;
  side?: MarketSide;
  entryPrice?: number;
  maxUserExposureUsd?: number;
  maxEventExposureUsd?: number;
  minNotionalUsd?: number;
  fractionalKelly?: number;
}): KellyExecutionPlan | null
```

核心逻辑：

1. 读取用户 profile、subscription、accounts、event、inventory。
2. 计算 bankroll：
   - 自助订阅用户：可用点数折算的交易额度 + 已充值账号钱包余额。
   - 托管用户：资产池可用额度或后台配置额度。
3. 过滤可交易账号：
   - `status !== disabled`
   - `canTrade = true`
   - `kycStatus = verified`
   - 有钱包地址或外部账号引用
4. 读取 AI 概率：
   - 当前先使用 `event.aiWinProbability`。
   - P0-2 后升级为强 AI evidence。
5. 调用 `calculateConstrainedKellySizing`。
6. 如果 `haltReasons` 非空，plan 状态为 `HALTED`。
7. 如果通过，使用 `sliceOrderAcrossAccounts(recommendedNotionalUsd, accounts)` 生成账号拆单。
8. 写入 `runtimeState.kellyPlans[planId]`。

## 五、API 行为变更建议

### 1. 修改 `/api/execution/context`

当前请求：

```json
{
  "userId": "user-alpha",
  "eventId": "EVT-001",
  "targetNotionalUsd": 15000
}
```

建议改为：

```json
{
  "userId": "user-alpha",
  "eventId": "EVT-001",
  "entryPrice": 0.52,
  "side": "YES"
}
```

返回：

```json
{
  "kellyPlan": { "...": "..." },
  "tradingContext": { "...": "..." }
}
```

关键变化：

- 不再要求 `targetNotionalUsd`。
- `recommendedNotionalUsd` 由 Kelly plan 生成。
- 如果 Kelly 失败，返回 plan，但 `status = HALTED`，不允许进入 intent。

### 2. 修改 `/api/execution/intents`

当前请求：

```json
{
  "userId": "user-alpha",
  "eventId": "EVT-001",
  "legs": [...]
}
```

建议改为：

```json
{
  "kellyPlanId": "KPLAN-..."
}
```

服务端行为：

- 根据 `kellyPlanId` 读取 approved plan。
- 根据 plan 的 `executionPlan` 和 event/platform 信息生成 legs。
- intent 写入 `kellyPlanId`。
- 如果 plan 过期、HALTED、用户不匹配、事件不匹配，则拒绝。

## 八、验收测试建议

### 单元测试

1. AI 概率高于价格，Kelly plan `APPROVED`，推荐仓位大于 0。
2. AI 概率低于价格，Kelly plan `HALTED`，halt reason 包含 `NO_EDGE`。
3. 用户点数/钱包余额为 0，halt reason 包含 `CAPITAL_UNAVAILABLE`。
4. 用户风险 cap 被现有库存占满，halt reason 包含 `RISK_CAP_EXHAUSTED`。
5. 推荐金额低于最小下单额，halt reason 包含 `MIN_NOTIONAL_NOT_MET`。
6. 账号未 KYC 或未充值，不进入可交易账号池。

### API 行为测试

1. `/api/execution/context` 不传 `targetNotionalUsd` 也能生成 Kelly plan。
2. `/api/execution/context` 返回 `HALTED` 时，`/api/execution/intents` 拒绝创建 intent。
3. `/api/execution/intents` 直接传 `legs` 被拒绝。
4. `/api/execution/intents` 传 approved `kellyPlanId` 成功创建 intent。
5. 创建出的 intent 包含 `kellyPlanId`。

## 九、预期影响

正向影响：

- 每笔自动化执行都有 Kelly 证据链。
- 用户无法绕过仓位计算直接提交超额交易。
- 后台可以审计 AI 概率、Kelly fraction、推荐金额和拆单计划。

需要注意：

- 现有测试中直接调用 `createIntent(userId, eventId, legs)` 的地方需要同步调整。
- 控制台如果未来展示执行模拟，需要先生成 Kelly plan。
- P0-2 未完成前，Kelly plan 的 AI 输入仍来自当前 `event.aiWinProbability`，后续应替换为强 AI evidence。
